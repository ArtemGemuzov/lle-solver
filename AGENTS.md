# Работа в lle-solver

- При изменении границ пакетов и логики запусков сверяйся с [ARCHITECTURE.md](ARCHITECTURE.md).
- Пиши комментарии на русском языке, а сообщения исключений — на английском.
- Используй только ASCII-символы и русские буквы при необходимости. Формулы в коде, комментариях и документационных строках записывай через `psi`, `delta`, `beta2`, `theta` и ASCII-операторы, без греческих букв, специальных математических символов и Unicode-индексов.
- В начале нового CLI-скрипта приводи пример вызова из корня репозитория. При изменении аргументов обновляй пример и проверяй вызов через CLI.
- Локально используй проектную `.venv`. На GPU-сервере работай в окружении conda из `environment.yml`. Команды приведены в разделе [Запуск на GPU-сервере](README.md#запуск-на-gpu-сервере).
- После изменений в `src/` или `scripts/` запускай из корня проекта `ruff check src scripts` и `ruff format --check src scripts`. Правила заданы в `pyproject.toml`. Если в Windows команда `ruff` недоступна в PATH, можно использовать `ruff.exe` из установленного расширения Ruff для VS Code.
- После изменений в `src/lle/` или в контрактах Import Linter запускай из корня проекта `uv run lint-imports`. Контракты в `pyproject.toml` проверяют граф из [ARCHITECTURE.md](ARCHITECTURE.md#граф-зависимостей).
- При изменении численного метода проверяй результат на небольшом примере с известным решением. Если изменение затрагивает фазу, сравнивай комплексное поле: интенсивность сама по себе фазовую ошибку не покажет.

- Оставляй `__init__.py` пустым без реальной необходимости. Не добавляй туда описания, переэкспорты или `__all__` ради удобства импортов. Используй прямые импорты из модулей.
- В комментариях и документационных строках описывай назначение кода, его поведение и неочевидные причины решений. Не перечисляй отсутствующие сущности или зависимости. Убирай комментарии, которые лишь повторяют очевидное из названия.
